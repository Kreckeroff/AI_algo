## 1. Что значит «обучить» в этом проекте

Не одна большая нейросеть. Два контура + продуктовые фичи без обучения весов:

| Контур | Что подбираем | Как |
|--------|---------------|-----|
| **A. Сигнал** | Веса/деревья модели на фичах бара | LightGBM / логрег на данных из Desktop |
| **B. Сборка** | Какие блоки, периоды, связи при недоопределённом промпте | LLM + паттерны/DSL; позже ранжировщик удачных графов |
| Compare / Advisor | — | Метрики + LLM-объяснение (веса не учим) |

**Выставление весов (A):** алгоритм обучения минимизирует ошибку на истории; веса руками не крутим.  
**Данные:** экспорт из IT Algo Desktop (свечи, индикаторы, составные ряды, графы/бэктесты) → ingest persist → CSV/Parquet.

**Управление обучением:** пользователь управляет агентом; агент создаёт/меняет артефакты скриптов и прогоны. См. [`work/AGENT_TRAINING_LOOP.md`](work/AGENT_TRAINING_LOOP.md). Прод UI — после качества модели.

## 2. Поток A (сигнал, CPU)

```text
Desktop / engine
  → экспорт датасета (CSV/Parquet)
  → фичи X + метка y (без look-ahead)
  → train / valid по времени (не shuffle)
  → LightGBM.fit
  → model.joblib (+ список фичей)
  → Desktop: те же фичи «сейчас» → predict_proba
```

### Черновая схема строки

| Группа | Примеры |
|--------|---------|
| Мета | `symbol`, `timeframe`, `ts` |
| Цена | OHLCV |
| Простые | `ret_1`, `rsi_14`, `atr_14`, `ema_dist_50` |
| Составные | `ema_5_of_rsi_14`, HTF-фильтры |
| `y` | напр. направление через N баров |

Железо: ноутбук, минуты. Без GPU для MVP.

---

## 3. Поток B (сборка стратегии)

```text
Промпт («трендовый на 5m»)
  → режим (trend / MR / breakout)
  → выбор паттерна из whitelist
  → периоды / пороги (defaults)
  → JSON графа (валидатор DSL)
  → опционально бэктест → отбраковка
```

Пользователь **не обязан** указывать RSI(14) vs RSI(21) и нужен ли `EMA(RSI)`. Система предлагает и объясняет допущения.

Позже: ранжировщик кандидатов графов по OOS-качеству (отдельное обучение, не LLM-weights).

## 4. Главные сложности

| # | Сложность | Как держим |
|---|-----------|------------|
| 1 | Комбинаторика индикаторы×периоды×вложенность×TF×инструменты | DSL + whitelist + max глубина; модель A только на раскрытых фичах |
| 2 | Смысл зависит от режима (`RSI>80` в тренде ≠ sell) | Режимы trend / MR / breakout в паттернах и фичах |
| 3 | Вложенность меняет ряд (`EMA(RSI)` ≠ RSI) | Composition в DSL; отдельные колонки фич |
| 4 | Look-ahead / переобучение | Фичи ≤ t; walk-forward; не shuffle |
| 5 | Шум рынка | Честный OOS; не обещать точность в продукте |
| 6 | Недоопределённый промпт | Defaults по режиму + объяснение допущений |
| 7 | Данные | Стабильный экспорт из приложения |

---

## 5. Иерархия против взрыва сложности

1. **DSL** — граф узлов (source = OHLCV или другой индикатор).
2. **Whitelist** composition-паттернов на MVP.
3. **Модель A** — на уже посчитанных числах выбранного графа.
4. **LLM/агент B** — предлагает граф; валидатор режет; бэктест отбраковывает.
5. Позже — **ранжировщик графов** по OOS.

## 5.1 Связь с продуктовой границей

Обучение кормится двумя путями (см. [`PRODUCT_BOUNDARY.md`](PRODUCT_BOUNDARY.md), [`work/platform/INTEGRATION_INTERFACES.md`](work/platform/INTEGRATION_INTERFACES.md)):

| Режим | Суть |
|-------|------|
| **Export** | Выгрузка нод + данных из Desktop → ingest/файлы → train в AI_algo |
| **Dev-integrated** | Ветка `dev`: живой ingest + Train API; promote в prod — отдельный шаг |

## 6. Практический порядок работ

1. Compare (продукт, почти без ML)  
2. DSL composition + режимы  
3. Builder + defaults  
4. Экспорт датасета + первый LightGBM  
5. Advisor  
6. Multi-TF → multi-instrument → graph ranker  

Первый эксперимент: 1 инструмент, 1 TF, 10–15 фич, метка на N баров → `experiments/`.

---

## 7. Критерии «можно в продукт» (A)

- [ ] Метрики на walk-forward / OOS приемлемы относительно baseline  
- [ ] Список фичей зафиксирован и совпадает с инференсом  
- [ ] Нет look-ahead в пайплайне  
- [ ] В UI — сигнал/режим + дисклеймер, не «прогноз прибыли»  
- [ ] Воспроизводимый скрипт обучения в `experiments/`
