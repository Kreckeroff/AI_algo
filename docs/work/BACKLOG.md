## Принцип

Это **не одна нейросеть**, а AI-слой из нескольких модулей с разной глубиной «своего»:

| Модуль | «Своя» модель? | Черновой приоритет |
|--------|----------------|--------------------|
| Конструктор скриптов из промпта | LLM + RAG + DSL; иногда сам подбирает блоки/веса | P0 |
| Сравнение версий скрипта (лучше/хуже) | Нет: метрики A/B + LLM-комментарий | **P0 / must-have** |
| Аналитик портфеля и статистики скриптов | Почти нет: правила + LLM | P1 |
| Прогноз / сигнал по рынку | Да, маленькая tabular-модель на CPU | P2 |
| **Композиция индикаторов + домен тренда/флэта** | DSL вложенности + обучение на составных фичах / политиках сборки | **идея ядра — обдумать** |

Стек по умолчанию: **каталог блоков + JSON Schema + RAG + LLM**. Обучение с нуля большой LLM — вне scope. Своя лёгкая модель (LightGBM и т.п.) — на данных из приложения, CPU-first.

**Важно:** RAG + сборка по готовым шаблонам — не единственный путь. Иногда пользователь **не уточняет** периоды, связки и веса — ИИ должна **сама предложить**, какие инструменты соединить и с какими параметрами (в рамках DSL и валидатора).

## 1. Конструктор скриптов из промпта

**Идея:** пользователь описывает стратегию текстом → ИИ собирает готовый граф/блоки в конструкторе (индикаторы, входы/выходы, риск, таймфрейм).

**Недоопределённый промпт (обязательный сценарий):**

> «Сделай трендовый скрипт на 5m»

Пользователь **не** сказал: RSI(14) или RSI(21), EMA(50) или EMA(200), нужен ли `EMA(RSI)`, какой TF фильтра, какие веса/пороги. ИИ должна:

- выбрать разумный набор блоков под **режим** (тренд / mean-reversion / breakout);
- проставить периоды, пороги, связи;
- объяснить допущения («взял EMA(50) как фильтр тренда, RSI сглаженный EMA(5) для входа…»);
- отдать валидный граф в конструктор.

**Черновые подзадачи:**

- [ ] DSL / JSON Schema скрипта как source of truth
- [ ] Каталог блоков + примеры для RAG
- [ ] Prompt → structured JSON (только валидные блоки)
- [ ] Политика defaults при недоопределении (по типу стратегии)
- [ ] Валидатор схемы + понятные ошибки пользователю
- [ ] Опционально: автозапуск бэктеста после сборки

**Статус:** backlog.

## 2. Сравнение версий скрипта — «стало лучше / хуже» *(критично)*

**Идея:** после изменения скрипта пользователь опрашивает ИИ: сравнить **было → стало** и получить комментарий — улучшилось ли, по каким метрикам, что ещё доработать.

**Почему отдельно от «просто аналитики»:** это основной цикл итерации трейдера/алго-разработчика, а не разовый отчёт.

**Черновой UX-поток:**

1. Пользователь правит скрипт (vN → vN+1) или выбирает две версии / два бэктеста.
2. Система считает (или подтягивает) сопоставимую статистику на **одинаковом** окне/рынке.
3. ИИ комментирует: лучше / хуже / смешанно, с опорой на цифры (не «на глаз»).
4. Даёт 1–3 конкретных совета по доработке (риск, фильтры, overfit, частота сделок и т.д.).

**Черновые подзадачи:**

- [ ] Версионирование скрипта (или явный выбор «до / после»)
- [ ] Сопоставимый бэктест / live-срез (одинаковый период, инструмент, комиссия)
- [ ] Diff метрик: PnL, max DD, winrate, Sharpe/Sortino, число сделок, avg R, exposure и т.п.
- [ ] Diff логики блоков (что изменилось в графе) — для объяснения «почему»
- [ ] Промпт/агент: только интерпретация метрик + diff, без выдуманных цифр
- [ ] Вердикт: `better` / `worse` / `mixed` + confidence / оговорки (мало сделок, другой режим рынка)
- [ ] UI: кнопка «Спросить ИИ про изменение» рядом с историей версий / после бэктеста

**Зависимости:** модуль аналитики метрик (п.3); желательно конструктор/DSL (п.1) для осмысленного diff блоков.

**Статус:** backlog — **обязательно учесть при укладке roadmap**.

## 6. Эксперимент: своя лёгкая модель на данных приложения

**Цель:** попробовать обучить CPU-модель на выгрузке из IT Algo — без GPU и без своего LLM.

**Черновая схема датасета (одна строка = один бар):**

| Группа | Примеры колонок |
|--------|-----------------|
| Мета | `symbol`, `timeframe`, `ts` |
| Цена | `open`, `high`, `low`, `close`, `volume` |
| Простые фичи | `ret_1`, `ret_5`, `rsi_14`, `atr_14`, `ema_dist_50` |
| Составные (позже) | `ema_5_of_rsi_14`, `rsi_14_on_htf`, … |
| Метка `y` | напр. `1` если `close[t+N] > close[t] * (1+ε)` |

**Поток:** экспорт из приложения → train/valid по времени → LightGBM → `model.joblib` → `predict` в Desktop/скрипте.

**Статус:** backlog / pet experiment.

## 7. Композиция индикаторов, режимы рынка и рост сложности *(ключевая идея)*

### 7.1 Суть

ИИ / модель должна уметь работать не только с «плоским» `RSI > 80`, а с **графом вычислений**, где индикаторы **вкладываются друг в друга**, плюс разные **инструменты**, **таймфреймы** и **периоды**.

Пример из продукта (трендовый контекст):

- Наивная mean-reversion логика: `RSI > 80` → «перекуплен → продавать».
- В **трендовом** скрипте `RSI > 80` часто наоборот признак **силы тренда**, а не сигнал на шорт.
- Если пропустить RSI через сглаживание, напр. `EMA(RSI)` или `SMA(RSI)`, ряд и пороги ведут себя **иначе** — появляется другая логика входов/фильтров тренда.
- Такие составные конструкции нужно **явно поддерживать в DSL** и **учитывать при обучении / подборе блоков**.

### 7.2 Что должно уметь пространство инструментов

| Ось сложности | Примеры | Зачем ИИ |
|---------------|---------|----------|
| Базовый индикатор | `RSI(14)`, `EMA(50)`, `ATR(14)` | каталог блоков |
| Параметры / периоды | `RSI(7)` vs `RSI(21)`, `EMA(20/50/200)` | defaults + поиск |
| Вложенность (composition) | `EMA(5, source=RSI(14))`, `RSI(source=HL2)` | трендовые/сглаженные сигналы |
| Комбинации | `price > EMA(50)` **и** `EMA(RSI) crosses up` | сборка скрипта |
| Мульти-ТФ | RSI на 5m + фильтр тренда на 1h | «трендовый скрипт» |
| Мульти-инструмент | сигнал на тикере A, фильтр/хедж на B | позже |
| Пороги и «веса» | 70/80, множители ATR, веса в скоринге | недоопределённый промпт |

Нейронка / AI-слой в итоге должна **жить в этом пространстве**, а не только в списке «голых» индикаторов.

### 7.3 Доменные режимы (чему учить / кодировать)

Не зашивать слепо «RSI>80 = sell». Нужны **режимы интерпретации**:

| Режим стратегии | Как читать RSI высокий | Типичные связки |
|-----------------|------------------------|-----------------|
| Mean-reversion | перекупленность → fade | RSI + BB / отклонение от MA |
| Trend-following | сила тренда → hold / add / filter | цена vs EMA + сглаженный RSI / ADX |
| Breakout | контекст сжатия → импульс | ATR squeeze + объём + HTF |

Идея обучения: не только веса фич, а ещё **политика «какой режим → какой набор блоков и порогов»** (через примеры графов, разметку, или отдельные головы модели).

### 7.4 Почему сложность взрывается

Число вариантов ≈  
`(индикаторы) × (периоды) × (source: price | другой индикатор) × (TF) × (инструменты) × (пороги)`.

Наивный перебор и «засунуть всё в одну сеть» — не взлетит. Нужна **иерархия**:

1. **DSL композиции** в конструкторе (граф: узел = индикатор, вход = OHLCV или выход другого узла).
2. **Ограниченный набор разрешённых composition-паттернов** для MVP (напр. `MA(any)`, `RSI(price|hlc3)`, HTF-filter).
3. **Лёгкая модель** — на уже **раскрытых** фичах выбранного графа (не на бесконечном пространстве).
4. **LLM/агент сборки** — предлагает граф; валидатор режет невозможное; бэктест отбраковывает слабое.
5. Позже — модель/бандит, которая **ранжирует** кандидатов графов (какие связки чаще живут на OOS).

### 7.5 Два разных «обучения» (не путать)

| Что учим | Вход | Выход | Железо |
|----------|------|-------|--------|
| **A. Сигнал на рынке** | значения фич на баре (в т.ч. составных) | вероятность / режим | CPU, LightGBM |
| **B. Сборка стратегии** | промпт + режим («трендовый») + каталог | граф блоков + периоды | LLM + правила; позже ранжировщик графов |

Пункт B — как раз «ИИ сама поняла, какие инструменты соединить и какие веса/периоды поставить», если пользователь не уточнил.  
Пункт A — «при таком `EMA(RSI)` и трендовом фильтре — какой сигнал».

Оба должны понимать **композицию**; это не только RAG.

### 7.6 Черновые подзадачи

- [ ] Формально описать composition в DSL low-code (source другого индикатора, TF, period)
- [ ] Каталог **паттернов** трендовых / MR / breakout (не сырые индикаторы)
- [ ] Примеры: `RSI>80` в тренде ≠ sell; `EMA(RSI)` как отдельный узел
- [ ] Экспорт составных рядов из движка для обучения модели A
- [ ] Политика автоподбора при недоопределённом промпте (модель B)
- [ ] Ограничители комбинаторики (whitelist composition, max глубина вложенности, max узлов)
- [ ] Мульти-ТФ и мульти-инструмент — фазы после single-symbol MVP
- [ ] Оценка: бэктест + OOS; для B — «собрал валидный трендовый граф без ручных периодов»

**Статус:** backlog / research — **зафиксировать как требование к ИИ-слою**.

## 8. AI сама гоняет бэктест + понимает блоки *(next product)*

**Почему сейчас только «Статистика» / метрики:** Phase 3 MVP — быстрый цикл «два прогона → вердикт» без оркестрации бэктеста. Это **не** конечная модель.

**Целевое поведение (согласовано с продуктовым запросом):**

1. ИИ видит **граф блоков** (не только периоды): добавление/удаление узлов, смена типа, параметров (`period`, пороги, source…).
2. ИИ может **сама запросить бэктест** через API Desktop (или агент Desktop: apply graph → `backtest_run` → вернуть metrics+graph).
3. Сравнение = metrics diff **+** graph diff **+** (опц.) советы что поменять в конструкторе.
4. UI: не только вкладка Статистика — также конструктор / после прогона (кнопка «Оценить изменение»).

**Черновые подзадачи:**

- [ ] Desktop: `POST` bridge / command `ai_run_backtest` (nodes/edges/range) → snapshot.stats + graph
- [ ] AI_algo intent `evaluate_change` / расширить `compare_scripts` (graph обязателен)
- [ ] Оркестратор: remember graph+metrics → user edits → AI may re-backtest both sides
- [ ] Вынести AI-панель из «только статистика» в общий scripting chrome
- [ ] Не сводить UX к «сменили period» — явный graph diff в ответе

**Статус:** backlog / принято как направление после Phase 3 MVP.
