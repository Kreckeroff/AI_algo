## Принцип

Это **не одна нейросеть**, а AI-слой из нескольких модулей с разной глубиной «своего»:

| Модуль | «Своя» модель? | Черновой приоритет |
|--------|----------------|--------------------|
| Конструктор скриптов из промпта | LLM + RAG + DSL; иногда сам подбирает блоки/веса | P0 |
| Сравнение версий скрипта (лучше/хуже) | Нет: метрики A/B + LLM-комментарий | **P0 / must-have** |
| Аналитик портфеля и статистики скриптов | Почти нет: правила + LLM | P1 |
| Прогноз / сигнал по рынку | Да, маленькая tabular-модель на CPU | P2 |
| **Композиция индикаторов + домен тренда/флэта** | DSL вложенности + обучение на составных фичах / политиках сборки | **идея ядра — обдумать** |

Стек по умолчанию: **каталог блоков + JSON Schema + RAG + LLM**. Обучение с нуля большой LLM — вне scope. Своя лёгкая модель (LightGBM и т.п.) — на данных из приложения, CPU-first.

**Важно:** RAG + сборка по готовым шаблонам — не единственный путь. Иногда пользователь **не уточняет** периоды, связки и веса — ИИ должна **сама предложить**, какие инструменты соединить и с какими параметрами (в рамках DSL и валидатора).

## 1. Конструктор скриптов из промпта

**Идея:** пользователь описывает стратегию текстом → ИИ собирает готовый граф/блоки в конструкторе (индикаторы, входы/выходы, риск, таймфрейм).

**Недоопределённый промпт (обязательный сценарий):**

> «Сделай трендовый скрипт на 5m»

Пользователь **не** сказал: RSI(14) или RSI(21), EMA(50) или EMA(200), нужен ли `EMA(RSI)`, какой TF фильтра, какие веса/пороги. ИИ должна:

- выбрать разумный набор блоков под **режим** (тренд / mean-reversion / breakout);
- проставить периоды, пороги, связи;
- объяснить допущения («взял EMA(50) как фильтр тренда, RSI сглаженный EMA(5) для входа…»);
- отдать валидный граф в конструктор.

**Черновые подзадачи:**

- [ ] DSL / JSON Schema скрипта как source of truth
- [ ] Каталог блоков + примеры для RAG
- [ ] Prompt → structured JSON (только валидные блоки)
- [ ] Политика defaults при недоопределении (по типу стратегии)
- [ ] Валидатор схемы + понятные ошибки пользователю
- [ ] Опционально: автозапуск бэктеста после сборки

**Статус:** backlog.

## 2. Сравнение версий скрипта — «стало лучше / хуже» *(критично)*

**Идея:** после изменения скрипта пользователь опрашивает ИИ: сравнить **было → стало** и получить комментарий — улучшилось ли, по каким метрикам, что ещё доработать.

**Почему отдельно от «просто аналитики»:** это основной цикл итерации трейдера/алго-разработчика, а не разовый отчёт.

**Черновой UX-поток:**

1. Пользователь правит скрипт (vN → vN+1) или выбирает две версии / два бэктеста.
2. Система считает (или подтягивает) сопоставимую статистику на **одинаковом** окне/рынке.
3. ИИ комментирует: лучше / хуже / смешанно, с опорой на цифры (не «на глаз»).
4. Даёт 1–3 конкретных совета по доработке (риск, фильтры, overfit, частота сделок и т.д.).
5. **Разбирает историю сделок** бэктеста: паттерны (пила, серии убытков, перекос сторон) → причина → что поменять в графе.

**Черновые подзадачи:**

- [ ] Версионирование скрипта (или явный выбор «до / после»)
- [ ] Сопоставимый бэктест / live-срез (одинаковый период, инструмент, комиссия)
- [ ] Diff метрик: PnL, max DD, winrate, Sharpe/Sortino, число сделок, avg R, exposure и т.п.
- [ ] Diff логики блоков (что изменилось в графе) — для объяснения «почему»
- [x] Разбор списка сделок (`trades[]`): эвристики пилы / hold / streak / long-short + советы по режиму
- [ ] Промпт/агент: только интерпретация метрик + diff + сделки, без выдуманных цифр
- [ ] Вердикт: `better` / `worse` / `mixed` / `unchanged` + confidence / оговорки
- [ ] UI: кнопка «Спросить ИИ про изменение» рядом с историей версий / после бэктеста
- [ ] (позже) Брокерская история сделок как доп. источник для Advisor

**Зависимости:** модуль аналитики метрик (п.3); желательно конструктор/DSL (п.1) для осмысленного diff блоков.

**Статус:** backlog — **обязательно учесть при укладке roadmap**.

## 7. Композиция индикаторов, режимы рынка и рост сложности *(ключевая идея)*

### 7.1 Суть

ИИ / модель должна уметь работать не только с «плоским» `RSI > 80`, а с **графом вычислений**, где индикаторы **вкладываются друг в друга**, плюс разные **инструменты**, **таймфреймы** и **периоды**.

Пример из продукта (трендовый контекст):

- Наивная mean-reversion логика: `RSI > 80` → «перекуплен → продавать».
- В **трендовом** скрипте `RSI > 80` часто наоборот признак **силы тренда**, а не сигнал на шорт.
- Если пропустить RSI через сглаживание, напр. `EMA(RSI)` или `SMA(RSI)`, ряд и пороги ведут себя **иначе** — появляется другая логика входов/фильтров тренда.
- Такие составные конструкции нужно **явно поддерживать в DSL** и **учитывать при обучении / подборе блоков**.

### 7.2 Что должно уметь пространство инструментов

| Ось сложности | Примеры | Зачем ИИ |
|---------------|---------|----------|
| Базовый индикатор | `RSI(14)`, `EMA(50)`, `ATR(14)` | каталог блоков |
| Параметры / периоды | `RSI(7)` vs `RSI(21)`, `EMA(20/50/200)` | defaults + поиск |
| Вложенность (composition) | `EMA(5, source=RSI(14))`, `RSI(source=HL2)` | трендовые/сглаженные сигналы |
| Комбинации | `price > EMA(50)` **и** `EMA(RSI) crosses up` | сборка скрипта |
| Мульти-ТФ | RSI на 5m + фильтр тренда на 1h | «трендовый скрипт» |
| Мульти-инструмент | сигнал на тикере A, фильтр/хедж на B | позже |
| Пороги и «веса» | 70/80, множители ATR, веса в скоринге | недоопределённый промпт |

Нейронка / AI-слой в итоге должна **жить в этом пространстве**, а не только в списке «голых» индикаторов.

### 7.3 Доменные режимы (чему учить / кодировать)

Не зашивать слепо «RSI>80 = sell». Нужны **режимы интерпретации**:

| Режим стратегии | Как читать RSI высокий | Типичные связки |
|-----------------|------------------------|-----------------|
| Mean-reversion | перекупленность → fade | RSI + BB / отклонение от MA |
| Trend-following | сила тренда → hold / add / filter | цена vs EMA + сглаженный RSI / ADX |
| Breakout | контекст сжатия → импульс | ATR squeeze + объём + HTF |

Идея обучения: не только веса фич, а ещё **политика «какой режим → какой набор блоков и порогов»** (через примеры графов, разметку, или отдельные головы модели).

### 7.4 Почему сложность взрывается

Число вариантов ≈  
`(индикаторы) × (периоды) × (source: price | другой индикатор) × (TF) × (инструменты) × (пороги)`.

Наивный перебор и «засунуть всё в одну сеть» — не взлетит. Нужна **иерархия**:

1. **DSL композиции** в конструкторе (граф: узел = индикатор, вход = OHLCV или выход другого узла).
2. **Ограниченный набор разрешённых composition-паттернов** для MVP (напр. `MA(any)`, `RSI(price|hlc3)`, HTF-filter).
3. **Лёгкая модель** — на уже **раскрытых** фичах выбранного графа (не на бесконечном пространстве).
4. **LLM/агент сборки** — предлагает граф; валидатор режет невозможное; бэктест отбраковывает слабое.
5. Позже — модель/бандит, которая **ранжирует** кандидатов графов (какие связки чаще живут на OOS).

### 7.5 Два разных «обучения» (не путать)

| Что учим | Вход | Выход | Железо |
|----------|------|-------|--------|
| **A. Сигнал на рынке** | значения фич на баре (в т.ч. составных) | вероятность / режим | CPU, LightGBM |
| **B. Сборка стратегии** | промпт + режим («трендовый») + каталог | граф блоков + периоды | LLM + правила; позже ранжировщик графов |

Пункт B — как раз «ИИ сама поняла, какие инструменты соединить и какие веса/периоды поставить», если пользователь не уточнил.  
Пункт A — «при таком `EMA(RSI)` и трендовом фильтре — какой сигнал».

Оба должны понимать **композицию**; это не только RAG.

### 7.6 Черновые подзадачи

- [ ] Формально описать composition в DSL low-code (source другого индикатора, TF, period)
- [ ] Каталог **паттернов** трендовых / MR / breakout (не сырые индикаторы)
- [ ] Примеры: `RSI>80` в тренде ≠ sell; `EMA(RSI)` как отдельный узел
- [ ] Экспорт составных рядов из движка для обучения модели A
- [ ] Политика автоподбора при недоопределённом промпте (модель B)
- [ ] Ограничители комбинаторики (whitelist composition, max глубина вложенности, max узлов)
- [ ] Мульти-ТФ и мульти-инструмент — фазы после single-symbol MVP
- [ ] Оценка: бэктест + OOS; для B — «собрал валидный трендовый граф без ручных периодов»

**Статус:** backlog / research — **зафиксировать как требование к ИИ-слою**.

## 7A. Фильтры vs сигналы входа + кросс-семейства + composition *(agent train wave)*

**Зачем:** в лаборатории v1 фильтр почти всегда был **EMA(50)**. На практике тренд часто режут **SuperTrend** (и другими): ST задаёт направление, отдельный блок даёт **только вход**. Нужен каталог **ролей**, не один EMA.

### Роли блоков (обязательно разделить)

| Роль | Что делает | Примеры |
|------|------------|---------|
| **Entry** | даёт момент входа (cross / breakout / reclaim) | RSI cross 50, MACD cross, Donchian break, Stoch cross |
| **Filter (trend / regime)** | разрешает сторону / запрещает торговлю против режима | **SuperTrend** (close>ST → только long), ADX>25 + DI, EMA/SMA slope, Donchian mid, HTF trend |
| **Exit / risk** | выход и риск | ATR SL/TP, opposite signal, time stop |
| **Composition source** | индикатор от индикатора | `EMA(RSI)`, `SMA(RSI)`, `RSI(HL2)`, `ATR% of close` |

**SuperTrend как фильтр (типичный паттерн):**

```text
trend = SuperTrend(period, mult)
entry  = <любое семейство входа>
long  = entry_long  AND close > trend   # или ST direction bullish
short = entry_short AND close < trend
```

ST здесь **не обязан** быть сигналом входа — часто только «где тренд», вход — RSI/MACD/Donchian/…

### Каталог фильтров (не только EMA) — заложить в DSL + train lab

- [ ] SuperTrend direction / price vs ST line  
- [ ] ADX + DI (сила + сторона)  
- [ ] EMA / SMA / dual MA slope (оставить как один из фильтров)  
- [ ] Donchian mid / price vs mid  
- [ ] Keltner mid / channel side  
- [ ] HTF filter (1h тренд при входе на 5m)  
- [ ] (позже) session / volatility regime  

В Builder / chat: ИИ должна уметь сказать «ставлю SuperTrend фильтром, вход по Donchian», а не всегда EMA(50).

### Ось периодов (не только 50)

В лабе нельзя зафиксировать один `period=50`. Нужно смотреть, **как ведут себя разные периоды** у entry и у filter.

**Диапазон периодов (обязательное правило):**

| Фаза | Диапазон `period` | Комментарий |
|------|-------------------|-------------|
| **Сейчас / C1–C2** | **1 … 200** включительно | жёсткий whitelist; значения вне диапазона — ошибка валидатора |
| **Позже** | расширять до **300**, затем **400** | отдельным флагом/экспериментом, не по умолчанию в prod defaults |

Сетки внутри 1–200 (MVP примеры, не единственные точки):

| Параметр | Пример сетки (whitelist ⊆ 1…200) |
|----------|----------------------------------|
| EMA / SMA filter | 20, 50, 100, 200 |
| SuperTrend | period 7/10/14 × mult 2/3 |
| Donchian entry / mid | 10, 20, 55 |
| RSI / Stoch / CCI | 7, 14, 21 |
| ADX | 14, 20 |
| ATR length | 7, 14, 21 (SL/TP множители отдельно) |

Сетка C1 по смыслу: **Entry(family, periods∈[1,200]) × Filter(kind, periods∈[1,200]) × TF × risk** — с budget.

Heatmap / ranking должны уметь резать по периоду (например EMA20 vs EMA200 при том же entry).
DSL/GraphDTO: `period` integer, constraint `1 ≤ period ≤ max_period` (`max_period=200` сейчас; 300/400 — feature flag).

### Движок бэктеста — переиспользуем

Прогоны комбинаций **не пишем с нуля** каждый раз:

| Слой | Роль |
|------|------|
| **Vectorized lab** (AI_algo experiments) | быстрый grid / sweep периодов, heatmap, отсев |
| **Тот же контракт метрик** (PnL, DD, WR, trades + trades[]) | сопоставимо с compare |
| **Desktop backtest engine** (`ai-train`) | валидация топ-кандидатов на реальном graph/`.italgo` |

Один пайплайн: lab sweep → shortlist → Desktop BT / ingest → compare. Параметры периодов — поля GraphDTO, не хардкод в коде фильтра.

### Волна комбинаторики (agent loop)

Не «одна гигантская сеть», а **систематический перебор графов** с лимитами:

| Волна | Что прогоняем | Ограничитель |
|-------|---------------|--------------|
| **C1** | Entry × Filter × **period grids** + risk v0/v1/v2 | whitelist фильтров; 1 filter; period whitelist; budget N прогонов |
| **C2** | Composition (`EMA(RSI)`…) × Filter × periods | max_depth = 2; whitelist composition |
| **C3** | Entry × Filter × **все доступные ТФ** + denser linkages | полный TF set из raw; budget только если wall-clock > лимита |
| **C4** | Два entry / stacking / HTF dual-filter | после C3 |

### Полное покрытие ТФ, связок и окон истории (обязательная цель обучения)

**Правило:** обучение стремится использовать **все доступные таймфреймы**, **все разумные связки** entry × filter × composition × indicator-period, и **кастомные окна истории** на каждом ТФ.

Различать два «периода» (не путать):

| Термин | Что | Диапазон |
|--------|-----|----------|
| **Indicator period** | параметр блока (EMA length, RSI length, Donchian…) | сейчас **1…200** (позже 300/400) |
| **History / lookback window** | длина истории бэктеста / куска данных на данном ТФ | **от 1 дня до 3–5 лет** (кастомные окна) |

| Ось | Цель |
|-----|------|
| **ТФ** | Все, что есть в raw/index: сейчас `1m, 5m, 10m, 15m, 30m, 1h, 1d, 1w, 1M` (+ Yahoo аналоги). Не ограничивать lab только 15m/1h/1d |

## 7H. Дивгэп на акциях / индексе — учесть в дообучении *(обязательно)*

**Проблема:** на **акциях** (и связанных **индексах**) в дату отсечки цена часто падает на дивгэп. В бэктесте «голый» OHLC это выглядит как прибыль шорта — **в реальности шорт дивгэп не зарабатывает**: дивиденд **списывают** с шорта (cash adjustment / borrow). Лонг формально «теряет» гэп, но получает дивиденд (в зависимости от модели учёта).

### Что это значит для AI / обучения

| Кейс | Реальность | Риск для модели |
|------|------------|-----------------|
| **Short через дивгэп** | Δ цены вниз ≠ PnL шорта; с счёта **забирают дивиденд** | Переоценка long/short стратегий, ложные «хорошие» шорты около ex-div |
| **Long через дивгэп** | Цена ↓, но дивиденд может компенсировать (если учтён) | Занижение PnL лонга, если дивиденд не в метриках |
| **Индекс** | Составные дивиденды / corporate actions влияют на ряд | Тот же bias на IMOEX / фьючерсах на индекс, если учимся на spot-like рядах |

### Правила для дообучения / улучшения (§7F + §7D)

1. **Не учить «сырой» шорт на акциях/индексе без модели дивгэпа** — либо корректировать PnL сделок через ex-div, либо помечать окна вокруг отсечек.
2. В датасете / features: флаги `near_ex_div`, `div_gap_pct`, `side=short`, `asset_class=equity|index` (когда появится календарь дивидендов).
3. Intervention / Advisor: для `long_short` на equities — советы «не держать шорт через отсечку» / «flat before ex-div» как отдельный kind вмешательства.
4. Сравнение LO vs LS (§7D): на дивидендных бумагах без корректировки **не** делать вывод «LS лучше» только из гэпов.
5. Фьючерсы / инструменты без дивгэпа — отдельный bucket; equities+index — bucket с §7H.

### Черновые подзадачи (P3.7)

- [ ] Источник календаря дивидендов / ex-div для MOEX equities (+ индексные компоненты)
- [ ] Правило cash adjustment в Desktop BT или post-hoc в AI_algo train (short: −div; long: +div optional)
- [ ] Разметка сделок / пар: `crossed_ex_div`, `div_adjusted_pnl`
- [ ] Дообучить intervention policy / ranker с фичами дивгэпа; ANALYTICS: heatmap near_ex_div × side

## 7D. Сторона позиции: long-only и long/short *(обязательно учитывать)*

## 7C. Цель оптимизации: PnL + winrate (с приоритетом по режиму)

**Зачем:** ИИ и ranker не должны оптимизировать «всё одинаково». Целевая функция зависит от типа скрипта.

### Общая цель

Нейросеть / AI-слой **стремится** к:

1. **положительному winrate** (где режим это допускает), и  
2. **максимальному чистому PnL**.

### Трендовые скрипты — особый приоритет

| Правило | Суть |
|---------|------|
| **Сначала PnL** | Для trend-following главный критерий — **net PnL** (и контроль DD), не WR |
| **WR &lt; 40% — норма** | У трендовых часто winrate ниже 40% — **не** помечать как провал |
| **Потом WR** | Задача: найти/улучшить **макс. PnL**, затем **пытаться поднять WR** до максимально возможного **без разрушения PnL** |

Порядок улучшения для тренда:

```text
1) максимизировать / стабилизировать net PnL (+ приемлемый max DD)
2) только потом — фильтры/выходы/состав, чтобы подтянуть winrate
```

Для MR и смешанных режимов — держать **оба** критерия явно; не копировать «PnL-only» слепо.

### Куда вшить

- [ ] Compare / verdict: для `regime=trend` вес PnL ≫ WR; не штрафовать WR∈[25%,40%] при сильном PnL
- [ ] Ranker / C1–C2 ranking: primary key = median/mean **PnL** (и DD), secondary = WR; для trend — WR только tie-break / phase-2
- [ ] Chat / Advisor: тексты советов по режиму (тренд ≠ «подними WR до 55% любой ценой»)
- [ ] Feature flag / policy table `regime → metric_weights` в AI_algo

**Статус:** product intent — **обязательная политика оптимизации**; 2026-08-21.
